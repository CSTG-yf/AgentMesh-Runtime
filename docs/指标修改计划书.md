## 一、当前指标体系的致命问题

### 🔴 P0 — 赛题公正性问题

#### 问题 1：`estimated_tokens` 两侧统计口径不一致

| 模式 | 代码位置 | 计算方式 |
|------|----------|----------|
| Text mode | `text_mode.py:93-94` | `estimate_tokens(task) + estimate_tokens(context)` — 累加原始任务 + 多轮累积上下文 |
| Protocol mode | `protocol_mode.py:500-501` | `estimate_tokens(task)` — **只算了原始任务文本** |

**后果**：当前对比表显示 Text 2077 tokens vs Protocol 9 tokens，其中 Protocol 的 9 根本不是协议开销，而是"task 文本估计出的 token 数"。这不是协议节省了 99.57% 的 token，而是**统计口径出错**。评委如果细看代码，会认为实验不严谨。

#### 问题 2：`wire_bytes` 两侧含义不同

Text mode 的 `wire_bytes` = 明文传递的文本字节数（`text_mode.py:96`）。
Protocol mode 的 `wire_bytes` = typed envelope wire bytes（`protocol_mode.py:503`）。

两者不是同一层级的对比。评委可能会质疑：为什么 text 那边 14562，protocol 只有 715？是因为协议真的如此高效，还是因为 **protocol 的 wire_bytes 只算了信封/引用，没算 payload 内容**？

#### 问题 3：Text mode 的 `estimated_tokens` 和 `wire_bytes` 也偏大

Text mode 每次传递的是**累积全量上下文**（`text_mode.py:85`），这在代码上看是故意"不优化"的 baseline。协议模式应该和"text mode 每次只传当前 agent 需要的最小内容"去比，才能说明协议的改进不只是"少传了冗余历史"。

### 🟠 P1 — 统计显著性 & 实验设计问题

#### 问题 4：`memory_hit_rate = 1.0000` 但只有 1 次查询

`protocol_mode.py:232` 写死 `memory_query_count = 1`。1 次命中率 100% 没有统计说服力。

**深层问题**：当前所有 memory metric 都是基于单次检索的结果。赛题要求"至少 2 组具有关联性的连续任务验证记忆复用"，当前缺乏：
- 任务 A → 写入记忆 → 任务 B（关联）→ 检索并复用 A 的记忆
- Cold start（无记忆）vs Warm start（有复用）的对照实验
- 跨任务复用率

#### 问题 5：`quality_preservation_rate` 已计算但未在主对比表展示

`benchmark.py:212` 已计算 `quality_preservation_rate = protocol_quality / text_quality`，`report.py:46` 也输出了，但 **`render.py` 的对比表中没有这个指标**。

评委想知道：协议模式节省了这么多 token，回答质量有没有下降？不展示这个指标，会给评委留下"故意隐瞒"的印象。

### 🟡 P2 — 指标冗余/展示不当问题

#### 问题 6：`memory avg tag overlap` 永远为 0

在当前 benchmark 中 `memory_avg_tag_overlap_score = 0.776`（仅在评分数据中有值，但在 `/compare` 渲染时 tag_overlap 未被实际填充），单次对比时渲染出来是 0.0000，反而暴露缺陷。

#### 问题 7：内部实现细节指标过多

`render.py` 当前展示了这些技术细节指标但评委不关心：
- `session_dictionary_bytes` — typed envelope 内部实现
- `typed_envelope_bytes` / `typed_payload_bytes` — 编解码细节
- `compact_structured_message_bytes` / `structured_message_bytes` — 多种序列化格式对比

这些指标在技术报告中可以提及，但在评审主表中会分散评委注意力。

### 🟢 P3 — 增强性建议

#### 问题 8：缺少按维度的收益率指标

当前只有三个 `_rate`（token、wire_bytes、latency）。缺少：
- **每消息 token 开销对比**：`total_tokens / messages` — 排除消息条数不同的干扰
- **每消息字节数对比**：`total_bytes / messages`
- **记忆带来的端到端节省**：有记忆的任务比无记忆的任务少花了多少 token

#### 问题 9：缺少 cold/warm 对比实验

赛题核心卖点是"跨任务记忆复用"，但当前没有设计冷启动 vs 热启动的实验。

## 三、逐指标修改方案

### 3.1 `estimated_tokens` — 口径修复（P0）

**涉及文件**：`protocol_mode.py:501`、`compare.py:270-273`、`metrics.py:68-75`

**当前问题**：
```python
# protocol_mode.py:501
estimated_tokens=estimate_tokens(task),    # ✗ 只算了任务文本
```
而 text mode 算的是 `estimate_tokens(task) + estimate_tokens(context)`。

**修改方案**：

方案 A（推荐）：在 `compare.py` 的 `_build_summary` 中统一计算可比较的 token 量

```python
# compare.py _build_summary 中新增
total_tokens_text = sum(
    estimate_tokens(output.input_summary) + estimate_tokens(output.output)
    for output in text_agent_outputs
)
total_tokens_protocol = sum(
    estimate_tokens(output.input_summary) + estimate_tokens(output.output)
    for output in protocol_agent_outputs
)
```

这样两边口径完全一致：都是"每个 agent 收到的 input + 产生的 output 的文本 token 总和"，消除了 text mode 因累积上下文导致的膨胀，也修复了 protocol mode 只计 task 的 bug。

方案 B（保守）：在 `protocol_mode.py` 中收集所有 agent I/O 文本

```python
# 在 protocol_mode.py run 函数中，收集所有 agent 的 input/output
all_agent_text = []
# 从 scheduler 或 messages 中提取每个 agent 的 input 和 output 文本
for msg in messages:
    if msg.result:
        all_agent_text.append(str(msg.result))
    if msg.params:
        all_agent_text.append(str(msg.params))
estimated_tokens = estimate_tokens(task) + sum(estimate_tokens(t) for t in all_agent_text)
```

**效果**：两边口径一致，评委可以信任 token 节省率。

### 3.2 `wire_bytes` — 定义清晰化（P0）

**涉及文件**：`compare.py:278-280`、`render.py:80-83`、`protocol_mode.py:503`、`text_mode.py:96`

**修改方案**：

1. 新增 `RunMetrics` 字段 `all_agent_io_bytes` — text mode 和 protocol mode 都统一计算"所有 agent I/O 的文本内容 UTF-8 字节总和"
2. text mode 的 `wire_bytes` 不变（纯文本累积上下文）
3. protocol mode 的 `wire_bytes` 改为 `protocol_envelope_wire_bytes` 以明确语义
4. 两边的 `all_agent_io_bytes` 作为公平对比的基准

### 3.8 Text mode 的 token 口径 — 增加按需传递模式对比（P3）

**涉及文件**：`text_mode.py`、`compare.py`

当前 text mode 每次传递的是**全量累积上下文**。虽然这是"最差情况"的 baseline，但为了更公平地展示协议的优势，应增加一个 text mode 的按需传递变体：

**在当前 text_mode.py 中**：
```python
# text_mode.py:93-96
# 保留 current 口径作为 "text_full_context"
# 新增口径：
estimated_tokens_per_agent_call = sum(
    estimate_tokens(response) for response in all_agent_responses
)
```

然后在 `compare.py` 中提供两套对比：
- **对比 1（最差 vs 最优）**：text_full_context vs protocol — 展示协议在长任务中的最大收益
- **对比 2（按需 vs 协议）**：text_per_agent vs protocol — 展示结构化协议本身的收益（排除冗余上下文传递的干扰）

> **注意**：这属于 P3 优先级，在 Sprint 0/1/2 完成后做。对比 1 是必选的，对比 2 是可选的补充视角。

### 3.9 新增 `agent_io_tokens` 统一口径（P2）

**涉及文件**：`metrics.py`、`protocol_mode.py`、`text_mode.py`

在 `RunMetrics` 中新增字段：

```python
class RunMetrics(BaseModel):
    # ... 现有字段
    agent_io_tokens: int = 0           # 所有 agent 实际输入/输出的 token 总和
    agent_io_text_chars: int = 0       # 所有 agent 输入/输出的文本字符总和
```

- text mode：`agent_io_tokens = sum(estimate_tokens(each_agent_input_or_output))`

这个口径是赛题"文本通信 token 或字符开销"最直接的对应指标。

## 四、关联连续任务设计

### 4.1 当前 benchmark 的不足

当前 `examples/benchmarks/long_context_tasks.yaml` 定义了 10 个任务（A1-A5, B1-B5）：
- 都在各自的 `input_file` 中独立提供上下文
- **没有任务间数据依赖关系**
- memory 可以检索到之前 task 写入的记忆（因为共享 store），但**没有设计实验验证这个效果**
- 每个 task 在 protocol mode 中 `memory_query_count` 恒为 1

**需要补充的两类实验**：
1. **AB 关联任务**：任务 A 产生知识 → 任务 B（关联任务）检索复用 A 的记忆
2. **Cold/Warm 对照**：同一关联任务 B，在有/无前置记忆的条件下各跑一次

### 4.2 新增 cross-task 依赖套件

新建 `examples/benchmarks/cross_task_ab.yaml`：

```yaml

  # 这些任务设计为"与 phase1 关联但不相同"，应能命中前序记忆
  # 例如：A1 分析了架构 → B1 要求基于架构分析做改进提案
  #      A2 设计了协议 → B2 要求实现协议的一个具体功能
```

```python
def _add_section_header(table: Table, title: str) -> None:
    table.add_row(f"[bold cyan]{title}[/bold cyan]", "", "")

def _add_row(table: Table, metric: str, text_val, protocol_val) -> None:
    table.add_row(
        metric,
        str(text_val) if text_val is not None else "—",
        str(protocol_val) if protocol_val is not None else "—",
    )

def _safe_div(numerator, denominator) -> float:
    if not denominator:
        return 0.0
    return round(numerator / denominator, 2)

def _render_latency_breakdown(console, summary):
    stage_ms = summary.protocol.metrics.stage_latency_ms
    if not stage_ms:
        return
    stage_table = Table(title="Protocol Mode Latency Breakdown")
    stage_table.add_column("Stage", style="cyan")
    stage_table.add_column("ms", justify="right")
    stage_table.add_column("%", justify="right")
    total = summary.protocol.metrics.latency_ms or 1
    for stage, ms in sorted(stage_ms.items(), key=lambda x: x[1], reverse=True):
        stage_table.add_row(stage, str(ms), f"{ms/total*100:.1f}%")
    console.print(stage_table)
```
